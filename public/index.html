V2T‑Search

Cross-modal multi-camera video retrieval — find driving behaviours from natural-language queries across a 2,900-clip, 4-camera dataset.

v2t-search.app — quad-camera retrieval
REEL 01 · v2t-demo-2.mp4 drop your clip — autoplays on deploy
The Problem

Standard video search matches appearance — "a red truck." It can't find behaviour — "an anxious driver changing lanes" — because the driver's state lives on the cabin camera and the lane change lives on the road camera, and no single embedding connects them.

What I Built

A retrieval system over 2,900 multi-camera clips with a synchronized 4-camera player. Three parallel layers — semantic scene embeddings, structured behaviour labels, and cross-camera co-occurrence — fused with Reciprocal Rank Fusion. Every result shows why it matched.

Architecture
Natural language query
        ↓
Query Planner (rules or Claude API)
        ↓
3 Retrieval Layers (parallel):
  · Semantic      — SigLIP2 + Qdrant
  · Behaviour     — PostgreSQL labels
  · Cross-camera  — SQL self-join
        ↓
Reciprocal Rank Fusion
        ↓
Ranked clips + Quad-camera player + "Why matched" panel
Key Engineering Decisions

One embedding can't hold "anxious" and "lane change" at once. I split it into three measurable layers and fused with RRF — no hand-tuned weights. Heavy compute (YOLO, SigLIP2) runs once at ingestion.

Honest Limitation

Cross-camera matching is co-occurrence, not temporal sequencing — the data is clip-level, not frame-level. The informative result is the gap between layers, not the final number alone.

Results / Evaluation
Results (48-query test set, human-verified ground truth):

Compound behaviour       | 0.04                      | 0.99
All query types          | 0.26                      | 0.95

Index: 11,568 clips · ~391,000 object vectors

FinAssist

Multimodal earnings-report assistant — every number computed in Python, every claim cited to its source page, and the system declines rather than guesses.

finassist.azurewebsites.net
Summary — Apple Q3 FY2025 metrics, every figure computed in Python with YoY %.
The Problem

Figures live in tables, context lives in narrative, trends live in charts — three surfaces analysts reconcile by hand. The biggest risk is citation errors and hallucinated numbers.

What I Built

An end-to-end multimodal RAG system with a 3-tab UI. Azure parses tables and figures; a vision model describes charts so they share one cite path. Hybrid retrieval finds passages; all numeric calculations run in deterministic Python — never the LLM.

Architecture
Earnings PDF
     ↓
Azure Document Intelligence (text + tables + figures)
     ↓
Hybrid Retrieval (BM25 + Vector RRF)
     ↓
Deterministic Python (numbers) + LLM prose
     ↓
Summary | Anomalies | Q&A + citations
Key Engineering Decisions

Numbers in Python, prose in the LLM — the core anti-hallucination guardrail. YoY deltas and margins are computed from source cells, not generated. Correct-refusal is enforced in prompts and verified live.

Honest Limitation

Mock-first: the full pipeline and 44 tests currently run at zero cost with no external Azure calls during standard test evaluation.

Ecom‑Ingest

A 4-agent listing pipeline — photo + seller notes become a policy-compliant, priced, SEO-ready listing. Zero API cost for blocked items.

ecom-ingest · streaming agents
REEL 03 · ecom-demo.mp4
The Problem

Listing at scale means either heavy cloud-AI spend per item or doing it by hand. The harder problem: counterfeit and policy-violating listings — if they reach the copywriting step, you've already paid to generate them.

What I Built

Vision → Pricing → Compliance → Copywriting. Each step uses the cheapest tool that works — local free models do detection, vision, pricing, compliance; a single cached Claude Haiku call writes the copy. The compliance gate runs before any paid call.

Architecture
Photo + seller notes
     ↓
Vision Agent (YOLO crop → Qwen2.5-VL local)
     ↓
Pricing Agent (OpenCLIP embed → ChromaDB)
     ↓
Compliance Agent (Regex + fuzzy + leetspeak)
     ↓
[BLOCKED?] → YES → Reject · $0.00
     ↓ NO
Copywriting Agent (Claude Haiku + prompt caching)
     ↓
Final SEO listing
Key Engineering Decisions

Cost routing — the hard call is which tool, not how. Leetspeak normalization catches "N1ke", "Gucc1"; seller notes are sandboxed against prompt injection; forced tool-use guarantees schema-valid output.

Code-Review Swarm

Adversarial multi-agent GitHub bot — a Proposer writes the patch, a Breaker attacks it in a sandbox, an Arbitrator judges the fight, and a human approves via Telegram before anything touches GitHub.

github.com · issue labeled swarm-fix → PR
PROPOSER → BREAKER → ARBITRATOR Langfuse trace + Telegram → GitHub PR · screenshot-ready
The Problem

Solo developers and small teams have no second pair of eyes before merging — but a single AI reviewer is too easy to trust blindly; it can confidently ship a wrong patch. So the AI argues with itself before a human ever sees it: one agent writes the fix, a second tries to prove it wrong, a third judges.

What I Built

Label an issue swarm-fix → a webhook fires → a Proposer writes a patch → it's applied to a throwaway repo and tested in a locked-down Docker sandbox (no network, memory-capped) → a Breaker attacks it using the test result as evidence → an Arbitrator judges approve/reject/revise → on approve, a Telegram verdict card waits for a human tap before a real PR opens.

Architecture
GitHub issue labeled swarm-fix
        ↓
Webhook (HMAC) → Redis Stream → ingestion worker
        ↓
LangGraph supervisor:
  Proposer   — writes patch
        ↓
  Docker sandbox — applies patch, runs tests (no network)
        ↓
  Breaker    — attacks patch using test results (blind to Proposer)
        ↓
  Arbitrator — approve / reject / revise (max 2 loops)
        ↓
[APPROVED] → Postgres-checkpointed interrupt → Telegram card
        ↓
Human taps Approve → graph resumes → GitHub PR opened
Key Engineering Decisions

Adversarial over single-agent — a lone LLM reviewing its own patch has no incentive to find its own mistakes; the Breaker is blind to the Proposer's reasoning, forcing a real argument. Failing tests hard-override the Arbitrator in code, not just a prompt. Durable HITL via a Postgres checkpointer — the approval pause survives a full process restart.

Expense IDP

Agentic expense-report processor — deterministic validation gates run before any LLM call, only genuinely ambiguous claims reach a human, and no API key exists anywhere.

expense-agent · receipt → decision
REEL 05 · expense_demo.mp4
The Problem

Manual expense review is slow and inconsistent — someone reads every receipt, checks policy, catches duplicates, decides approve/reject. This automates the clean 90% and routes only genuinely ambiguous or risky claims to a human, without letting the LLM be a single point of failure on fraud.

What I Built

Drop a receipt into a web UI → a vision LLM reads it into structured data → deterministic checks (totals, caps, FX, duplicates, staleness) run first → a policy-RAG judge checks real company policy text → an orchestrator auto-approves, auto-rejects, or escalates to a human queue (web or Teams Adaptive Card) → approved claims post to a mock ERP and the submitter is notified.

Architecture
Browser (drag-drop receipt)
        ↓
Ingest — vision extraction (gpt-5.4-mini)
        ↓
Validate — deterministic checks
           (totals · caps · FX · duplicates · staleness)
           + policy RAG judge (Azure AI Search)
        ↓
Decide (rules engine)
  Auto-approve | Auto-reject | Escalate
        ↓ (escalate)
HITL pause → Teams Adaptive Card → human resolves
        ↓
Post to mock ERP → notify → persist (Cosmos DB)
Key Engineering Decisions

Deterministic gates before the LLM — totals, caps, FX, duplicates and receipt-presence are pure functions the model can never override, proven against an injection-laced receipt. Protocol-based providers so mock and real Azure run the exact same code path. Restart-safe HITL. Zero API keys anywhere — everything authenticates via Entra ID / Managed Identity.

Honest Limitation

No accuracy/latency benchmarks against a labeled receipt dataset yet — end-to-end verified on real Azure once, not load-tested.

PureOS

Native iOS diagnostic suite for a ZYD-controller electric scooter — built by reverse-engineering an undocumented binary BLE protocol from raw packet captures.

REEL 04 · scoot_demo.mp4
The Problem

The manufacturer app exposes almost no diagnostics. As a hardware technician I needed live motor current, draw, battery state, temperature and odometer — plus ride-mode and light control — with no documentation. The whole protocol had to be inferred from raw wireless packets.

What I Built

A SwiftUI app — Login, BLE Radar Scan, live Dashboard. It authenticates with an AT+PWD handshake to GATT characteristic F2F1, polls at 1 Hz, and renders speed, current, power, voltage, battery, temperature and odometer. ECO / DRIVE / SPORT and lights switch in real time.

Architecture
Device Scan → AT+PWD Handshake to F2F1 → 1 Hz Polling

Protocol: F0... (25-byte and 23-byte variants) and AB... packets.
Commands: Signed with CRC16-MODBUS checksums.
Key Engineering Decisions

Two packet families (F0… in 25- and 23-byte variants, plus AB…) with no spec. Every field was inferred by diffing raw hex against the scooter's physical display. Command frames are signed with CRC16-MODBUS — invalid checksums are rejected.

Honest Limitation

Firmware OTA upload doesn't work yet — the genuine open problem. The command/telemetry channel is fully functional.

Results / Evaluation
Values confirmed against the scooter's own display · corrected an off-by-one byte error (6169.6 → 2033 km)

- 2 packet families decoded
- 1 Hz polling heartbeat
- 2033 km odometer verified
- 18 HIL commands tested

ScooterHub

Full-stack warehouse & repair workflow app — digitizing the complete electric-scooter repair lifecycle across 5 staff roles with a shared mechanic job queue and a full audit trail.

scooterhub · workshop queue → QC
REEL 07 · warehouse-demo.mp4
The Problem

Repair shops running warranty and B-grade repairs on paper or spreadsheets lose track of case status, parts consumption and mechanic workload. This digitizes the whole lifecycle — intake → triage → payment review → repair → QC → dispatch — with role-based views so each person sees only what's relevant to their job.

What I Built

A full-stack internal ops app covering the whole repair lifecycle. The mechanic workshop is a claim-based shared queue (any mechanic claims any available job, one active at a time) with a live elapsed timer, a drag-reorderable task checklist that gates completion, inline parts consumption against stock, auto-saving notes, and a pause-for-parts flow. QC is checklist pass/fail; dispatch handles labels and tracking — all with a full audit trail and role-scoped permissions.

Architecture
Mechanic clicks Claim
        ↓
POST /api/cases/[id]/claim (RBAC + concurrency guard)
        ↓
Prisma transaction
  (status + mechanicId + RepairTimeLog + StatusHistory)
        ↓
Workshop job → TaskList · PartsPicker · NotesField
        ↓
Mark complete → status → QUALITY_CONTROL
Key Engineering Decisions

A separate /claim endpoint over overloading start-repair — distinct responsibilities, then deleted the old path once replaced. Sequential integer task ordering — simplest for 5–20 tasks; only changed rows PATCH on reorder. No websockets — refresh-based state is enough for a workshop floor. A Transactional Outbox with Trigger.dev workers handles reliable async.

What It Covers
5 staff roles · role-scoped views throughout
Claim-based shared mechanic queue (1 active job each)
Live repair timer + gating task checklist
Inline parts consumption vs. stock
Full audit trail — CaseStatusHistory + AuditLog
