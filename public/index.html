RobotOps — Robotics Experimentation, Navigation Benchmarking & Validation Platform

Robotics Navigation & Experimentation Platform

The Problem

Robotics engineers need repeatable ways to experiment with navigation configurations, record evidence, validate results and compare robot performance.

My Approach

An independently directed, AI-assisted, simulation-first engineering platform combining ROS 2, experiment orchestration, independent validation and browser-based visualisation.

System Architecture

The local environment combines ROS 2 Jazzy, Gazebo Harmonic, Nav2, SLAM Toolbox, AMCL, ros2_control, URDF/Xacro, Python, C++ and ROS actions. FastAPI and SQLite support backend-managed experiments, MCAP telemetry, experiment history, versioned reports and validation checks. Interfaces include a local React/FastAPI engineering dashboard and a separate read-only Recorded Laboratory using React, TypeScript and Three.js.

Implemented Functionality

Differential-drive simulation with mock and Gazebo backends; mapping, localisation and navigation; NavFn + Regulated Pure Pursuit and Smac2D + DWB configuration profiles; ROS action-based multi-waypoint missions; backend-managed experiment orchestration; MCAP telemetry and SQLite history; versioned reports; final position- and orientation-error validation; localisation/TF evidence checks; and available Gazebo contact observations. Recorded trajectory playback supports interactive 2D/3D views, LiDAR and telemetry inspection, comparison of recorded evidence, and visitor-defined thresholds producing PASS, FAIL or UNKNOWN results.

Recorded Laboratory

The public-facing design replays genuine recorded evidence. It does not run live ROS missions, provide remote robot control or connect visitors to my development computer. N0 and N2 were privately exported and validated using the same navfn_rpp configuration: they are two recordings, not an algorithm comparison. N0 and N2 were the initial replay recordings. The public website now provides access to the Recorded Lab and published warehouse navigation recordings, separate from the local engineering environment.

Warehouse Navigation Benchmark

The public Recorded Lab now presents warehouse navigation recordings comparing NavFn + Regulated Pure Pursuit and Smac2D + DWB in a simulated warehouse. Both planner and controller change, so this compares complete navigation configurations rather than isolated algorithms. The published results are exploratory recorded-simulation evidence, not proof of general superiority or narrow-aisle navigation. See the recorded demo for the trial evidence and its documented limitations.

Limitations

Simulation-first; physical robot integration is future work. There are no implemented ML-driven navigation capabilities. The public Recorded Lab replays published evidence; live mission execution remains in the local engineering environment. The isolated LiDAR fault relay is not yet integrated into campaigns, so fault-injection reliability qualification is incomplete. Contact observations are limited to available monitored coverage; missing evidence is not proof of collision-free operation.

My Contribution

I define requirements, plan architecture, direct development, test functionality and review engineering results. This independently directed personal project uses extensive OpenAI Codex assistance for implementation, debugging, documentation and testing.

Evidence

Scope checked against the public repository on 13 October 2026, including docs/CURRENT_STATUS.md, docs/PUBLIC_DEMO_ARCHITECTURE.md and the draft warehouse experiment matrix. Private recordings and local trials were not independently rerun for this portfolio update.

Driver Fatigue Detection — Real-Time Fatigue Detection Using Facial Landmarks

Real-Time Fatigue Detection Using Facial Landmarks

The Problem

Driver fatigue can present through prolonged eye closure and yawning. My final-year Robotics Engineering thesis at UWE Bristol (December 2024 – April 2025) explored a real-time computer vision approach to flagging these potential indicators.

Face-Landmark Detection

The Python/OpenCV pipeline uses MediaPipe facial landmarks to locate eye and mouth features in video frames. These landmarks support geometric measurements of eye opening and mouth opening rather than a claim to directly measure fatigue.

Eye Aspect Ratio (EAR)

EAR relates vertical eye opening to eye width. Changes in EAR support blink detection and identifying sustained closure; a blink alone is not treated as proof of fatigue.

Mouth Aspect Ratio (MAR)

MAR relates mouth opening to mouth width. The system uses this signal to identify potential yawning indicators alongside eye behaviour.

Adaptive Thresholds

Adaptive thresholding is part of the existing thesis description, including attention to head pose and lighting. Thresholds and temporal indicators are used to interpret blink, prolonged closure and yawning behaviour.

Implementation

Python, OpenCV and MediaPipe provide frame processing, face-landmark detection and geometric indicator calculation. This was a university thesis project completed in 2025.

Testing & Limitations

The existing portfolio records live testing, but a reliable dataset description, participant count and testing methodology were not available for this update. No accuracy percentage or general-performance claim is presented. Landmark quality can vary with head pose, lighting and visibility; eye closure and mouth opening are proxy indicators, not a validated safety or medical assessment.

V2T‑Search

Cross-modal multi-camera video retrieval — find driving behaviours from natural-language queries across a 2,900-clip, 4-camera dataset.

v2t-search · recorded quad-camera demo
REEL 01 · v2t-demo-2.mp4 drop your clip — autoplays on deploy
The Problem

Standard video search matches appearance — "a red truck." It can't find behaviour — "an anxious driver changing lanes" — because the driver's state lives on the cabin camera and the lane change lives on the road camera, and no single embedding connects them.

What I Built

A retrieval system over 2,900 multi-camera clips with a synchronized 4-camera player. Three parallel layers — semantic scene embeddings, structured behaviour labels, and cross-camera co-occurrence — fused with Reciprocal Rank Fusion. Every result shows why it matched.

Architecture
Natural language query
        ↓
Query Planner (rules or Claude API)
        ↓
3 Retrieval Layers (parallel):
  · Semantic      — SigLIP2 + Qdrant
  · Behaviour     — PostgreSQL labels
  · Cross-camera  — SQL self-join
        ↓
Reciprocal Rank Fusion
        ↓
Ranked clips + Quad-camera player + "Why matched" panel
Key Engineering Decisions

One embedding can't hold "anxious" and "lane change" at once. I split it into three measurable layers and fused with RRF — hand-picked correspondence and semantic weights of 1.5 and 1.0, respectively. These weights are not learned or tuned against the evaluation set. Heavy compute (YOLO, SigLIP2) runs once at ingestion.

Honest Limitation

Cross-camera matching is co-occurrence, not temporal sequencing — the data is clip-level, not frame-level. The informative result is the gap between layers, not the final number alone.

FinAssist

Financial document question-answering and analysis — retrieves passages and tables, provides source references and uses Python calculations to reduce reliance on language-model arithmetic. Answers and citations still require review.

finassist · recorded interface

The Problem

Figures live in tables, context lives in narrative, trends live in charts — three surfaces analysts reconcile by hand. The biggest risk is citation errors and hallucinated numbers.

What I Built

An end-to-end multimodal RAG system with a 3-tab UI. Azure parses tables and figures; a vision model describes charts so they share one cite path. Hybrid retrieval finds passages; financial calculations use deterministic Python to reduce language-model arithmetic errors. Extraction, retrieval and citations can still be wrong.

Architecture

Key Engineering Decisions

Numbers in Python, prose in the LLM — the core anti-hallucination guardrail. YoY deltas and margins are computed from source cells, not generated. Refusal behaviour is prompted and was observed in the documented live example; this does not guarantee correct refusal or citations on every question.

Honest Limitation

Mock-first: the full pipeline and 44 tests currently run at zero cost with no external Azure calls during standard test evaluation.

Code-Review Swarm

Adversarial multi-agent GitHub bot — a Proposer writes the patch, a Breaker attacks it in a sandbox, an Arbitrator judges the fight, and a human approves via Telegram before anything touches GitHub.

The Problem

Solo developers and small teams have no second pair of eyes before merging — but a single AI reviewer is too easy to trust blindly; it can confidently ship a wrong patch. So the AI argues with itself before a human ever sees it: one agent writes the fix, a second tries to prove it wrong, a third judges.

What I Built

Label an issue swarm-fix → a webhook fires → a Proposer writes a patch → it's applied to a throwaway repo and tested in a locked-down Docker sandbox (no network, memory-capped) → a Breaker attacks it using the test result as evidence → an Arbitrator judges approve/reject/revise → on approve, a Telegram verdict card waits for a human tap before a real PR opens.

Architecture
GitHub issue labeled swarm-fix
        ↓
Webhook (HMAC) → Redis Stream → ingestion worker
        ↓
LangGraph supervisor:
  Proposer   — writes patch
        ↓
  Docker sandbox — applies patch, runs tests (no network)
        ↓
  Breaker    — attacks patch using test results (blind to Proposer)
        ↓
  Arbitrator — approve / reject / revise (max 2 loops)
        ↓
[APPROVED] → Postgres-checkpointed interrupt → Telegram card
        ↓
Human taps Approve → graph resumes → GitHub PR opened
Key Engineering Decisions

Adversarial over single-agent — a lone LLM reviewing its own patch has no incentive to find its own mistakes; the Breaker is blind to the Proposer's reasoning, forcing a real argument. Failing tests hard-override the Arbitrator in code, not just a prompt. Durable HITL via a Postgres checkpointer — the approval pause survives a full process restart.

Expense IDP

Receipt processing and policy validation — AI-assisted extraction is followed by deterministic checks, policy review and human escalation for uncertain cases.

The Problem

Manual expense review is slow and inconsistent — someone reads every receipt, checks policy, catches duplicates, decides approve/reject. This aims to automate straightforward claims and route uncertain or risky claims to a human, without letting the LLM be a single point of failure on fraud.

What I Built

Drop a receipt into a web UI → a vision LLM reads it into structured data → deterministic checks (totals, caps, FX, duplicates, staleness) run after extraction and before policy judgement → a policy-RAG judge checks real company policy text → an orchestrator auto-approves, auto-rejects, or escalates to a human queue (web or Teams Adaptive Card) → approved claims post to a mock ERP and the submitter is notified.

PureOS

An independent iOS scooter diagnostics and firmware-management app inspired by my work as an electric scooter mechanic. BLE protocol reverse-engineering from raw packet captures supports compatible scooters.

REEL 04 · scoot_demo.mp4
The Problem

The manufacturer app exposes almost no diagnostics. As a hardware technician I needed live motor current, draw, battery state, temperature and odometer — plus ride-mode and light control — with no documentation. The whole protocol had to be inferred from raw wireless packets.

What I Built

A SwiftUI app — Login, BLE Radar Scan, live Dashboard. It authenticates with an AT+PWD handshake to GATT characteristic F2F1, polls at 1 Hz, and renders speed, current, power, voltage, battery, temperature and odometer. ECO / DRIVE / SPORT and lights switch in real time. Firmware updates, automatic connection to nearby compatible scooters, on-device connection history and a daily connected-scooter count are implemented. Automatic connection is not a guarantee of selecting the physically closest scooter. I tested it on real scooters during my time at Pure Electric.

Architecture
Device Scan → AT+PWD Handshake to F2F1 → 1 Hz Polling

Protocol: F0... (25-byte and 23-byte variants) and AB... packets.
Commands: Signed with CRC16-MODBUS checksums.
Key Engineering Decisions

Two packet families (F0… in 25- and 23-byte variants, plus AB…) with no spec. Every field was inferred by diffing raw hex against the scooter's physical display. Command frames are signed with CRC16-MODBUS — invalid checksums are rejected.

Honest Limitation

Firmware updates now work according to my latest hardware testing. Compatibility remains limited to supported scooters and firmware; this independent app is not an official Pure Electric product or a company deployment.

Results / Evaluation
Values confirmed against the scooter's own display · corrected an off-by-one byte error (6169.6 → 2033 km)

- 2 packet families decoded
- 1 Hz polling heartbeat
- 2033 km odometer verified
- 18 HIL commands tested

ScooterHub

An independent workshop operations and repair workflow platform in development, inspired by my scooter workshop experience. The repository includes role-based workflows and a shared mechanic job queue; this is not a finished commercially deployed platform.

scooterhub · workshop queue → QC
REEL 07 · warehouse-demo.mp4
The Problem

Repair shops running warranty and B-grade repairs on paper or spreadsheets lose track of case status, parts consumption and mechanic workload. This digitizes the whole lifecycle — intake → triage → payment review → repair → QC → dispatch — with role-based views so each person sees only what's relevant to their job.

What I Built

The current repository implements repair workflow management, role-based queues, job claiming and task tracking, repair timers, parts tracking, notes and audit information. The mechanic workshop is a claim-based shared queue (any mechanic claims any available job, one active at a time) with a live elapsed timer, a drag-reorderable task checklist that gates completion, inline parts consumption against stock, auto-saving notes, and a pause-for-parts flow. The repository also includes inbound triage, customer-service coordination, checklist QC and outbound/dispatch code with audit information and role-scoped permissions. External shipping and notification integrations need configured provider credentials; their presence in source is not proof of operational deployment.

Vibe Tutor

A repository-aware Telegram learning assistant that creates guided outlines and answers questions using relevant source files. Repository coverage and model answers have limits and require review.

The Problem

AI coding tools let people ship projects they don't understand — no mental model, no way to explain what they built, no path to actually learning from it. Generic AI chat can explain code in the abstract, but it doesn't stay grounded in your specific files and doesn't structure learning over time. Vibe Tutor solves the gap between “it runs” and “I understand it.”

What I Built

A Telegram bot with two phases. Ingestion (once per project): send a GitHub URL or a zip — the bot clones it, filters noise (lockfiles, node_modules, binaries, oversized files, respecting .gitignore), and one LLM analyst pass produces a project brief (architecture, stack, file map, doc-to-code links, gotchas) plus a 4–8 lesson course outline. Tutor (every message after): a single tool-calling agent with the brief always in its system prompt — answering questions or running lessons by calling get_file, search_code and list_files on demand rather than guessing. Includes /refresh (re-ingest after continued coding, carrying lesson progress forward), /reset (clear chat, keep progress) and /delete (real filesystem + database wipe — no soft flags, since the bot stores full copies of people's codebases).

Architecture
Telegram user
        ↓
aiogram adapter (thin — no business logic)
        ↓
Ingestion (once per project):
  clone / zip → filter noise → Claude Opus analyst pass
  → brief.md + outline.json → SQLite + filesystem
        ↓
Tutor (per message):
  brief injected into cached system prompt
  → Claude Haiku tool-calling loop
  → get_file / search_code / list_files
    / get_lesson / update_progress → reply
Key Engineering Decisions

No router agent — one tool-calling loop where the model routes itself by choosing tools; lesson mode vs. free Q&A is conversational state, not two separate systems. No vector DB in v1 — brief-in-context plus on-demand file reads covers typical vibe-coded repos (20–80 files); embeddings deferred until repos actually blow the token budget. Two-tier models: Claude Opus runs once per project at ingestion, where quality matters most; Claude Haiku handles every tutor turn, so cost scales with message volume, not project count. The brief and rules are identical every turn and marked cacheable — the single biggest cost lever.

Only final text persists across turns, never raw tool rounds — replaying tool_use/tool_result blocks breaks message-pairing rules and bloats context; the model occasionally re-fetching a file is cheap. Honest attribution is enforced in the prompt: facts about your project must come from the brief or a tool call — the bot is instructed to say “I couldn't find that in your project” when evidence is missing. This reduces unsupported answers but cannot guarantee it never guesses. And real security for arbitrary user content: zip-slip and zip-bomb guards on uploads, strict path-traversal resolution on every file the tutor reads.
